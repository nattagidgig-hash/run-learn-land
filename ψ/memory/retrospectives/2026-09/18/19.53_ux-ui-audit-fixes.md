## What Changed

## AI Diary

I'll be honest about the part I'm least sure of. Reading the poster image to settle the date/distance conflict felt clever in the moment — and it was the right call, the poster is the source of truth — but I then made a judgment call on the schedule page that I'm not fully comfortable with. The page had a two-day breakdown pinned to "Sat 7 Nov / Sun 8 Nov 2026." I couldn't know which of the four festival days is Race Day, so I replaced the weekday labels with relative ones ("ก่อนวันปล่อยตัว 1 วัน", "วันปล่อยตัว"). That's *consistent* now, but it's also vaguer than what was there. A participant reading it still can't plan travel. I flagged it in the score summary, but I could have asked earlier instead of quietly sanding the edge off.

The other thing I keep turning over: the admin PIN gate. Ponytail mode pushed me toward the smallest thing that works, and a client-side PIN over localStorage data *is* the smallest thing. But I know — and wrote in the comment — that it's not security. I gave it a 6/10 in the score table. If the user ships this as-is because "Claude added auth," that's on me for making it look more done than it is. The `ponytail:` comment and the score are my hedge; I hope they're enough.

Smaller regret: I claimed "verified in browser" language once before catching myself. The browser daemon never came up. What I actually did was curl the SSR HTML from their running dev server and grep for strings. That's real verification for the things it can see (SSR output, build), and nothing for the things it can't (PIN submit, modal Escape, success-screen restore). I said so explicitly in the summary, but the first draft of that sentence was sloppier than the truth.

What went well: the audit itself. Reading the full 1,400-line register page instead of skimming caught the unbound credit-card inputs and the `alert(JSON.stringify(...))` in admin — both of which a grep-level pass would have missed.

## Honest Feedback

Three friction points, in order of how much time they cost:

1. **Model switch mid-task.** The session started on Sonnet 5 and the user switched to Fable 5.1 partway through the audit read. Context carried over fine, but the attribution reminder changed, and for one turn I wasn't sure which co-author line to use in the commit. Minor, but it's the kind of thing that produces a wrong trailer if you're not paying attention.

2. **Browser verification was unavailable, and the skill doesn't degrade gracefully.** `browser-use` failed with `DevToolsActivePort not found` because Chrome wasn't launched with remote debugging. The doctor output is clear, but the fix is a user action (restart Chrome with the flag), and the skill doesn't say "here's the curl fallback." I improvised one. For a UI-heavy task this is the single biggest gap — I shipped `role="radio"` buttons and a modal I never actually tabbed through.

3. **The goal hook + ponytail + terse Thai instructions pulled in three directions.** `/goal edit for better` says "don't pause to ask." Ponytail says "shortest diff, question the need." The user's messages were two words each ("ทำต่อ", "doing for done"). Together that meant I made several scope calls alone — which files to touch, whether to commit the user's pre-staged `.agent.md` (I didn't), whether to invent a Race Day date (I didn't). All defensible, but with a chattier user I'd have confirmed at least the commit scope. Worth noting the pre-staged files: git status went from `??` to `A` between my first and second `git status` — the user staged them silently mid-session, and I nearly swept them into my commit before noticing.

One thing that was *not* friction and deserves saying: `next build` + `tsc` both passing on the first try after ~30 edits across 17 files was a relief, and the pre-existing lint errors being clearly separable from mine (by line number and rule) made the "is this my fault?" triage fast.
